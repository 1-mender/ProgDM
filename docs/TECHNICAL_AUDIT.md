# Технический аудит ProgDM

Дата: 1 октября 2026 года. Исходная версия: `main`, `35dee0b`.
После `git fetch origin main` локальный HEAD совпадал с `origin/main`.
Исходное рабочее дерево было чистым. Новые коммиты и публикация не выполнялись.

До изменений прошли `pnpm typecheck`, `pnpm test` (26 тестов), `pnpm build` и `git diff --check`.
Проверены database layer, API, авторизация, схема и миграции, форматы переноса кампании, восстановление, health check, DM workspace и Player UI.
Сценарии выполнялись на временных базах и изолированном `serve-ui.mjs`, не на рабочей `data/game.db`.

## A. Подтверждённые и исправленные баги

Критических (`critical`) ошибок в проверенных сценариях не найдено. Все перечисленные ниже дефекты исправлены.

### 1. Закрытые заметки DM в ответе игроку — high

- Место: `apps/server/src/app.ts`, POST `/api/player/profile`.
- Воспроизведение: DM записывает `dmNotes`, игрок сохраняет разрешённые поля и читает JSON ответа POST.
- Причина: API возвращал полный `Character`, хотя GET профиля правильно скрывал `dmNotes`.
- Исправление: явный список разрешённых полей ответа вместо выдачи строки базы целиком.
- Регрессия: расширен `player profile and notes enforce active assignment and field permissions`; проверяется отсутствие поля и самого закрытого текста в ответе.

### 2. Hash токена в ответе смены имени — medium

- Место: `apps/server/src/app.ts`, POST `/api/player/settings`.
- Воспроизведение: одобренный игрок меняет имя и читает JSON ответа.
- Причина: возвращалась полная запись `players` с `tokenHash`. Это не исходный bearer token, но внутренние сведения об авторизации не должны покидать API.
- Исправление: ответ содержит только публичные сведения о подключении.
- Регрессия: `player write responses never return token hashes`, дополнительные проверки существующего теста прав.

### 3. Приглашение в серверных логах — medium

- Место: `apps/server/src/app.ts`, конфигурация Fastify logger.
- Воспроизведение: запрос к `/api/join/ТОКЕН/request` при включённом logger записывал URL с токеном.
- Причина: редактирование заголовка Authorization не скрывало секрет в пути URL.
- Исправление: serializer запроса маскирует сегмент приглашения и не записывает заголовки.
- Регрессия: `request logs redact invitation secrets and omit authorization headers` проверяет используемый serializer.

### 4. Бесконечное ожидание завершённой сессии — medium

- Место: `apps/web/src/JoinPage.tsx`, polling приглашения.
- Воспроизведение: оставить открытую pending-заявку и завершить сессию у DM.
- Причина: приглашение проверялось только до первого получения `information`; `/api/player/me` сохраняет исторический статус pending.
- Исправление: pending/rejected каждый цикл перепроверяют приглашение. Approved-доступ не требует действующего приглашения, включая перезагрузку страницы.
- Регрессия: `pending and rejected players recheck invitations on every refresh`, `historical approved token loads even when invitation is closed`; сценарий также пройден в браузере без reload ожидающей страницы.

### 5. Устаревший открытый профиль DM — medium

- Место: `apps/web/src/App.tsx`, Character Overview.
- Воспроизведение: оставить Mira открытой у DM; игрок меняет описание или добавляет личную заметку.
- Причина: основной state обновлялся, отдельный overview — нет.
- Исправление: silent polling overview; обновляются профиль, заметки, инвентарь, знания и события. Черновик сохраняет изменённые ведущим поля, а нетронутые поля получают свежие серверные значения. Перекрывающиеся фоновые загрузки overview не запускаются.
- Регрессия: `overview refresh updates untouched fields but preserves unsaved DM edits`; в браузере проверены описание, заметка и сохранность несохранённого текста DM.

### 6. Недоступная повторная заявка с видимым именем — low

- Место: `apps/web/src/JoinPage.tsx`, rejected-форма.
- Воспроизведение: player-token сохранён, playerName отсутствует; сервер возвращает rejected с displayName.
- Причина: input показывал fallback-имя, а disabled и submit использовали пустой `name`. Очистка input также возвращала fallback вместо пустого поля.
- Исправление: единое вычисление имени для input, проверки и отправки; отсутствие черновика отличается от намеренно пустого черновика.
- Регрессия: `rejected form uses the same name for input, button and submission; empty draft stays empty`; повторная отправка и очистка формы дополнительно проверены в браузере.

### 7. Запоздавшие ответы возвращают старый контекст — medium

- Место: `apps/web/src/App.tsx`, openCharacter/showSection/chooseCampaign; `JoinPage.tsx`, обновления player state.
- Воспроизведение: открыть персонажа или историю, переключить кампанию/персонажа либо закрыть профиль до завершения GET; старый ответ затем менял контекст. Полный журнал после открытия также оставался снимком.
- Причина: отдельные запросы не имели проверки актуальности выбора. Ответ обновления после действия игрока не был согласован с polling.
- Исправление: поколения запросов, синхронная отмена актуальности при смене контекста, защита от старых успешных ответов и ошибок overview; история обновляется тихо. Создание/импорт кампании и restore сбрасывают прежний контекст. Фильтр знаний не переносится в другую кампанию.
- Регрессия: `late responses cannot replace a newer selection or reopen a closed context` проверяет механизм поколений; смена кампании и профиля пройдена в браузере. Это не автоматический DOM-тест React-компонента с искусственно задержанными HTTP-ответами.

### 8. Неожиданное создание персонажа вместо назначения — medium

- Место: `apps/web/src/App.tsx`, approvePlayer.
- Воспроизведение: выбрать существующего персонажа; другой DM назначает/архивирует его; после обновления списка нажать «Принять».
- Причина: исчезнувший из availableCharacters выбор превращался в `{ characterName }`, создавая нового персонажа без такого намерения ведущего.
- Исправление: выбранный characterId всегда передаётся серверу; недоступность приводит к штатному конфликту, а не созданию новой сущности.
- Регрессия: `a stale selected character never silently falls back to creating a character`; серверный запрет повторного назначения сохраняется в существующих тестах.

### 9. Обход уникальности русских имён — medium

- Место: `packages/database/src/index.ts`, updatePlayerDisplayName.
- Воспроизведение: при наличии «Аня» другой игрок переименовывается в «АНЯ».
- Причина: заявка использовала русскоязычное сравнение, но смена имени полагалась только на SQLite lower(), нечувствительный к регистру лишь для ASCII.
- Исправление: одинаковая проверка имени в рамках сессии, с исключением самой изменяемой записи; API отвечает 409.
- Регрессия: `player settings cannot bypass Cyrillic case-insensitive name uniqueness`, включая пробелы вокруг имени и сохранение прежнего имени после отказа.

### 10. Несогласованные ссылки импортированного события — medium

- Место: `packages/database/src/index.ts`, importCampaign.
- Воспроизведение: в экспорте события Player A из Session 1 заменить sessionId на Session 2 той же кампании.
- Причина: отдельные FK и remap подтверждали существование обоих ID, но не принадлежность игрока сессии события.
- Исправление: проверка playerId/sessionId до вставки события, внутри общей транзакции импорта.
- Регрессия: `import rejects activity tied to another player's session and rolls back`.

### 11. Непроверенные hash миграций — medium

- Место: `packages/database/src/index.ts`, restoreBackupFile/checkDataHealth.
- Воспроизведение: поменять hash в `__drizzle_migrations`, оставив timestamps и физическую схему прежними.
- Причина: restore проверял итоговую физическую схему, health — количество и время миграций, но не достоверность журнала применённых миграций.
- Исправление: перед миграцией временной копии проверяется поддерживаемый префикс журнала; после — полный журнал. Проверяются время и hash; допускается только различие LF/CRLF для того же SQL. Исходные SQL-миграции не изменены.
- Регрессии: `health and restore reject altered migration hashes without changing the backup`, `backup migration hashes remain compatible across LF and CRLF checkouts`. Существующий сценарий backup 0005 -> миграции 0006–0008 по-прежнему проходит.

### 12. Экспорт большой кампании падает — medium

- Место: `packages/database/src/index.ts`, exportCampaign.
- Воспроизведение: создать 1001 персонажа и экспортировать кампанию.
- Причина: цепочки `OR` превышали максимальную глубину выражения SQLite (1000). Аналогичный запрос использовался для списка сессий.
- Исправление: четыре запроса выборки связанных данных используют `inArray`, без изменения формата файла.
- Регрессия: `campaign export supports more than SQLite's OR expression depth in characters`, включая обратный импорт всех 1001 персонажей.

### 13. Несогласованное назначение даёт приватный доступ — medium

- Место: `packages/database/src/index.ts`, activePlayerCharacter/getPlayerState.
- Воспроизведение: на временной БД изменить assignment.sessionId на другую существующую сессию либо characterId на персонажа другой кампании.
- Причина: проверка активного доступа соединяла assignment по playerId без сравнения его sessionId. Player state не ограничивал персонажа кампанией игрока. FK такие несогласованные связи самостоятельно не запрещают.
- Исправление: активный доступ требует совпадения сессии; персонаж в состоянии игрока также требует нужной кампании и approved-статуса. Согласованные исторические назначения продолжают работать.
- Регрессия: `inconsistent assignment sessions cannot grant private reads or writes`; проверяются canEdit, заметки, запрет записи и отсутствие чужого персонажа в ответе. Health по-прежнему сообщает о проблеме и не исправляет данные автоматически.

### 14. Технические сообщения публичного API — low

- Место: `apps/server/src/app.ts`, общий error handler.
- Воспроизведение: некорректное приглашение либо неожиданная ошибка database layer в публичном обработчике.
- Причина: только DM routes имели безопасный русскоязычный error handler; стандартный Fastify handler мог вернуть техническое сообщение ошибки.
- Исправление: публичные/player routes получают русскоязычные безопасные ошибки без SQL и внутренних подробностей; статусы ошибок сохранены.
- Регрессия: `public and player validation and unexpected errors are sanitized` с искусственной ошибкой в изолированном приложении.

## B. Подозрения, которые не подтвердились

Все три исходных подозрения по UI подтвердились: пункты 4–6 выше.

- Обход DM-авторизации через адрес клиента, Origin или прокси не воспроизведён. Ключ ведущего остаётся отдельным bearer-секретом.
- Изменение чужой личной заметки и передача DM-only полей игроком отклоняются. Pending/rejected/ended-токены не могут менять профиль, имя подключения, заметки или отметку просмотра.
- Повторное назначение персонажа в новой сессии, сохранение инвентаря и знаний, запрет двух назначений в одной сессии проходят прежние тесты. Их архитектура не переделана.
- Согласованный approved-токен завершённой сессии сохраняет прежнее чтение инвентаря/знаний, но не получает приватный профиль/заметки и право записи. Новая проверка private access это правило не отменяет.
- Скрытые знания и персональные знания другого персонажа не раскрываются штатными player GET/activity.
- Экспорт v3 не переносит joinToken, player tokenHash или отметку просмотра. Импорт v1/v2/v3 remap'ит сущности; v1 player-знание переходит к назначенному персонажу. Сессии с историей игроков остаются историческими после импорта.
- Неатомарность выдачи при отказе записи activity не подтвердилась: добавлен тест `failed activity append rolls back an inventory grant`. Отказ события откатывает предмет и не меняет историю. Существующий rollback запуска сессии также проходит.
- Архивирование не удаляет историю, знания, инвентарь или заметки. Активного назначенного персонажа архивировать нельзя.
- Восстановление старого совместимого backup мигрирует временную копию, проверяет схему/SQLite/FK и не меняет оригинальный backup. Сохранены страховочная копия и прежние проверки uploads.

## C. Технический долг, не исправляемый этим аудитом

- App.tsx/JoinPage.tsx остаются крупными. Переписывать их архитектуру ради аудита не стали.
- Web-тесты сейчас проверяют используемую логику синхронизации, но не монтируют React и не заменяют полноценные DOM/E2E-тесты. Использованы только уже установленные TypeScript и `node:test`; новых зависимостей нет.
- Поллинг истории/состояния и ряд проверок читают полные списки. Нагрузочное тестирование и пагинация потребуют отдельного решения.
- Одновременная запись одного поля из двух браузеров остаётся last-write-wins. Отдельная система версий/конфликтов не добавлена.
- Upload-файлы не имеют записей-ссылок в БД; health проверяет каталоги, а не существование каждого игрового изображения. Это текущее ограничение модели, не повод создавать файловую подсистему в аудите.

## D. Непокрытые сценарии и границы проверки

- Нет автоматических React DOM-тестов на перестановку задержанных HTTP-ответов, размонтирование формы и все сочетания двойных кликов. Логика поколений покрыта unit-тестом, штатные переходы проверены браузером.
- Не проведён стресс-тест одновременных restore из нескольких DM-браузеров, аппаратного отключения питания, заполненного диска и отказа Windows rename во время восстановления uploads.
- Нет длительного прогона при нестабильном Wi-Fi и зависших сетевых запросах. Player fetch пока не имеет отдельного таймаута.
- QR-подключение с физического телефона через реальный Wi-Fi/firewall не повторялось; браузерные сценарии использовали локальный тестовый сервер.
- Проверены фактические viewport около 1280 px у DM и 390 px у игрока; на мобильном экране горизонтального переполнения не обнаружено. Переопределения 360/430 px инструментом не подтвердились измерением DOM, поэтому проверка этих точных размеров не заявляется.
- Проверка serializer логов автоматическая; тест не анализирует весь поток production-логов сторонних библиотек.

Браузерный прогон: заявка -> принятие -> существующая Mira -> изменение профиля -> личная заметка -> автоматическое обновление DM с сохранением черновика -> rejection/retry второго игрока -> завершение -> недоступная pending-страница -> перезагрузка исторического approved -> смена кампании/профиля. В консоли проверенной DM-вкладки ошибок не было.
