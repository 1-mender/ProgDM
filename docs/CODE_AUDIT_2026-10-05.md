## Подтверждённые ошибки

### F1. P1: повтор подключения после потерянного ответа меняет токен

Код: `apps/web/src/JoinPage.tsx:81`, `:83`, `:99`.

Новый токен сохраняется в localStorage до POST, но React `credential` меняется
только после успешного ответа. Если сервер уже создал заявку, а ответ потерян,
`credential` остаётся пустым. Повтор отправки генерирует другой токен и
перезаписывает сохранённый первоначальный. Сервер возвращает конфликт имени,
поскольку первая заявка уже существует. Перезагрузка после такого повтора не
восстанавливает исходный доступ: сохранён уже второй токен.

Воспроизведение: первый POST принят, ответ симулирован как потерянный; второй
submit фактического JoinPage использовал другой токен. Проверка API отдельно
подтвердила 409 при том же имени и другом токене. Исходный токен после повтора
отсутствовал в localStorage.

Рекомендация: сохранять pending credential также в состоянии, повторно
использовать его при неопределённом результате и проверять `/api/player/me`
перед заменой. Учитывать гонку polling и ещё не завершившегося POST: ранний 401
не должен уничтожать credential выполняющейся заявки.

Нужен регрессионный тест: сервер принял join, ответ потерян, повтор и reload
сохраняют доступ к той же записи Player без новой заявки и конфликта имени.

### F2. P1: idempotency инвентаря не переживает смену вкладки

Код: `apps/web/src/player/InventoryPage.tsx:27`, `:65`, `:78`, `:85`;
`apps/web/src/player/PlayerWorkspace.tsx:92`.

Operation IDs неопределённых transfer/discard хранятся в `useRef` внутри
InventoryPage. Смена вкладки размонтирует компонент, а возвращение создаёт
новую карту. После операции, выполненной сервером без полученного клиентом
ответа, повтор того же действия получает новый operationId. Backend правильно
считает его отдельной операцией и снова уменьшает stack.

Воспроизведение фактического обработчика discard: stack 5, сервер списал 1,
клиент получил ambiguous; remount и повтор списали ещё 1 с другим operationId.
Осталось 3 вместо 4. Отдельная DB-проверка подтвердила, что два разных IDs
действительно выполняют две операции. Закрытие sheet без remount само по себе
карту не уничтожает.

Рекомендация: registry неопределённых операций должен жить вне вкладки,
сохранять исходный intent и ID при переходах. Для восстановления после reload
нужна долговечность pending intent или явное согласование результата перед
новой отправкой. Изменение quantity/получателя не должно незаметно превращать
повтор неопределённого действия в новую операцию.

Нужны тесты потерянного ответа, навигации, reload, partial transfer/discard и
повторной отправки с тем же ID без двойного изменения inventory/activity.

### F3. P2: допустимый русский текст превышает HTTP body limit

Код: `apps/server/src/app.ts:42`.

Общий Fastify `bodyLimit` равен 4096 байтам, тогда как схемы ограничивают
длины строк в символах и допускают более крупные JSON-запросы. Кириллица
занимает несколько байтов; несколько разрешённых полей суммируются.

API-воспроизведения:

- Разрешённые shortDescription 500, personalGoal 500, appearance 1000,
  quote 300 символов `я`: JSON 4680 байт, ответ 413.
- Разрешённые title 120 и body 2000 символов `я` у заметки:
  JSON 4295 байт, ответ 413.

Пользователь может заполнить форму в рамках всех её ограничений и не суметь
сохранить данные. Риск распространяется также на многострочные DM-формы.

Рекомендация: ограниченные route-specific body limits, согласованные с
максимальным UTF-8 размером валидных payloads; schema validation сохранить.
Для 413 нужен понятный русский ответ.

Нужны API-тесты максимальных допустимых кириллических строк и отклонения
действительно слишком большого запроса.

### F4. P2: собственный экспорт длинной кампании нельзя импортировать

Код: `packages/database/src/index.ts:140`, `:1061`, `:1131`;
дополнительный HTTP-предел: `apps/server/src/app.ts:412`.

Экспорт отдаёт всю историю без ограничения числа событий. Импорт через
`transferArray` отклоняет любой массив длиннее 10000. Длительная кампания
может экспортироваться успешно, но её собственный архив уже не пройдёт импорт.
Дополнительно HTTP import ограничен 10 MiB, а export не ограничен этим размером.

Воспроизведение: изолированная кампания с 10002 activity records экспортирована
в корректный v11 JSON размером 3641333 байта, ниже HTTP-предела. Обратный DB-import
отклонил файл с `Campaign file is invalid.`. Частичный импорт не произошёл.

Рекомендация: согласовать ресурсные ограничения экспортёра и импортёра так,
чтобы поддерживаемая кампания проходила round-trip. Не обрезать историю молча.
Если ограничение продукта сохраняется, экспорт должен явно предупреждать,
что создаваемый архив нельзя восстановить текущим импортёром.

Нужен round-trip тест кампании с историей больше 10000 событий и тест политики
для файла, превышающего HTTP-предел.

### F5. P2: черновик профиля теряется при polling, а отмена его не сбрасывает

Код: `apps/web/src/player/ProfilePage.tsx:22`, `:65`, `:88`.

Эффект при изменении любого серверного поля переписывает все локальные поля
редактора, даже во время ввода. Изменение DM личной цели через polling
уничтожает несохранённое описание игрока. Отмена только закрывает editor,
не восстанавливая данные: повторное открытие показывает отменённый текст.

Оба случая воспроизведены исполнением фактических обработчиков/эффектов:
после cancel/reopen оставался `Cancelled text` вместо `Stored text`;
после обновления другой серверной строки `Unsaved player draft` заменялся
на `Stored text`.

Рекомендация: отдельный lifecycle черновика — snapshot при начале,
discard при отмене, защита dirty fields от polling и явная политика конфликтов.
В DM уже есть `mergeProfileDraft`, который можно учитывать как существующий
локальный подход, не переписывая всю систему профиля.

Нужны UI-тесты cancel/reopen, polling во время редактирования и сохранения
при параллельном изменении другого поля.

### F6. P2: открытая хроника не обновляется вместе с PlayerState

Код: `apps/web/src/player/JournalPage.tsx:26`, `:45`;
`apps/web/src/player/PlayerWorkspace.tsx:73`.

Journal хранит собственный массив событий. Первая страница загружается при
переключении tabs или смене callback; callback стабилен для credential.
Polling обновляет PlayerState и «Новое», но не перечитывает хронику.
Новые события не появляются до повторного открытия раздела.

Воспроизведение: после изменения props с одного свежего события на два
фактический effect не инициировал второй запрос; timeline сохранил одну запись.
В уже загруженном списке также нет согласования с новой видимостью знаний:
после revoke может оставаться прежняя строка и переход к уже недоступной записи.
Это устаревший клиентский snapshot, а не доказательство выдачи нового
скрытого текста сервером.

Рекомендация: обновлять свежую страницу/согласовывать события при новых данных,
сохраняя pagination и позицию прокрутки; пересматривать visibility-sensitive
строки при изменении доступных знаний.

Нужны UI-тесты события во время открытой хроники, изменения grants/visibility,
deduplication и сохранения более ранних страниц при обновлении.

### F7. P2: скачивание ведущим не имеет timeout и может заблокировать workspace

Код: `apps/web/src/App.tsx:94`, `:378`, `:403`, `:696`, `:727`.

Обычный request имеет AbortController, но downloadFile использует fetch и
response.blob без timeout. Экспорт/скачивание backup выполняются внутри mutate.
Если соединение зависло до заголовков или во время тела, promise не завершается,
и finally не освобождает busy; действия ведущего остаются заблокированы.

Подтверждено трассировкой исходного пути выполнения; реальное зависание сети
в браузере отдельно не симулировалось.

Рекомендация: ограничить весь download, включая чтение body, обеспечить
освобождение состояния и возможность повторно скачать уже созданный backup
без обязательного создания ещё одной копии.

Нужны тесты зависшего fetch/body, освобождения busy и успешного retry.

### F8. P3: повторное восстановление персонажа нарушает тип ответа

Код: `packages/database/src/index.ts:2402`.

Если персонаж уже не архивный, restoreCharacter возвращает raw Drizzle record,
где traits является JSON-строкой. Реальное восстановление использует
characterRecord и возвращает массив. Идемпотентный вызов имеет другой формат.

API-воспроизведение: 200 с `traits: "[]"` вместо `traits: []`.
Текущий DM UI обновляет snapshot и не использует этот response, поэтому
падение текущей формы не наблюдалось. Ошибка касается shared/API-контракта.

Рекомендация: применять один record adapter во всех ветках.
Нужен тест одинакового Character response при первом и повторном restore.

## Существующие механизмы и остаточные риски

- Проверенные DB/API tests проходят, включая active controller authorization,
  исторические назначения, facts projection, inventory atomicity, staged restore
  и очистку сессий/игроков. Обход этих проверок в аудитных сценариях не найден.
  Это не доказательство отсутствия всех возможных ошибок безопасности.
- Разрешённое историческое чтение approved token не классифицируется как баг:
  это существующее продуктовое решение. Его изменение здесь не предлагается.
- `projectPlayerActivity` (`packages/database/src/index.ts:660`) обрабатывает
  накопленную релевантную историю перед сокращением результата. Polling каждого
  игрока и journal pagination могут дорого обходиться в длинной кампании;
  следует измерить нагрузку. Отдельный SLA/нагрузочный тест не выполнялся.
- Значимая часть web tests проверяет source patterns или чистые helpers.
  Они не обнаружили перечисленные ошибки lifecycle. Нужен небольшой
  исполняемый UI-слой для сетевой неопределённости, remount, dirty drafts и polling,
  а не только дополнительные regex assertions.
- Браузерный focus trap, keyboard navigation, реальные LAN interruptions,
  одновременные действия с физических телефонов и mobile layout в этом аудитном
  прогоне не проверялись. Эти пункты не отмечены как успешно пройденные.
