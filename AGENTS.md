# Заметки по проекту ProgDM

## Направление продукта

ProgDM — локальное веб-приложение для настольных ролевых игр и ведущих. Ведущий запускает приложение на ноутбуке, а игроки подключаются с телефонов через локальную Wi-Fi сеть или точку доступа по ссылке или QR-коду.

Для работы не должны требоваться установка приложения игроками, регистрация по электронной почте, интернет, облачные серверы, Docker, PostgreSQL или микросервисная инфраструктура.

Путь игрока:

1. Открыть ссылку вида `http://АДРЕС-НОУТБУКА:ПОРТ/join/ТОКЕН`.
2. Ввести имя.
3. Дождаться подтверждения ведущего.
4. Получить назначенного персонажа.
5. Перейти к текущей части игры, доступной игроку.

## Текущий стек

- TypeScript.
- React и Vite в `apps/web`.
- Node.js и Fastify в `apps/server`.
- Рабочие пространства pnpm.
- Локальное хранение: SQLite, Drizzle ORM и better-sqlite3.
- Zod может быть добавлен для проверки данных во время выполнения, когда это потребуется функции.
- Socket.IO может быть добавлен для обмена событиями в реальном времени, когда это потребуется функции.

## Границы рабочих областей

- `apps/web` — веб-интерфейс ведущего и игроков.
- `apps/server` — локальный HTTP API и, при необходимости в будущем, шлюз событий сессии.
- `packages/shared` — общие типы предметной области и константы.
- `packages/database` — схема SQLite, миграции, управление подключением и операции кампании/сессии.
- `packages/game-engine` — независимые от интерфейса вспомогательные функции кампаний и сессий.

Рабочие данные хранятся здесь:

- `data/game.db`
- `data/uploads/monsters`
- `data/uploads/characters`
- `data/uploads/items`
- `data/backups`

## Модель предметной области

Модель предметной области:

`Campaign -> Characters -> Inventory`

`Campaign -> Sessions -> Players -> SessionCharacterAssignments -> Characters`

Персонаж и его инвентарь принадлежат кампании и сохраняются между сессиями. `Player` относится только к одной сессии; назначение персонажа этому игроку хранится отдельно и не переносит постоянное владение на запись игрока. Для одной сессии один игрок может иметь не более одного персонажа, а один персонаж не может быть назначен двум игрокам. Исторические назначения не удаляются при завершении сессии. Ведущий сохраняет полный контроль. Действия игроков должны оформляться как запросы, которые ведущий может подтвердить или отклонить. Справочник предметов и записи знаний подготавливаются до игры; игрок видит только инвентарь назначенного ему персонажа и сведения, явно открытые ведущим.

## Функции продукта

ProgDM — общая память партии и пульт ведущего, управляющий тем, что известно игрокам. Приложение помогает игрокам видеть вещи своих персонажей и открытия партии, а ведущему — быстро выдавать предметы и открывать сведения.

Боёвка, сражения, инициатива, очки здоровья, урон и лечение исключены из области проекта, а не отложены на будущее. Не добавляй связанные модели данных, события, элементы управления или пункты плана, если пользователь явно не изменит это решение. Монстры остаются записями знаний, видимость которых контролирует ведущий.

Основные экраны игрока должны показывать:

- профиль игрока и назначенного персонажа;
- инвентарь этого игрока;
- известные задания, персонажей мира, монстров и заметки;
- только сведения, которые явно открыл ведущий.

Основные инструменты ведущего должны обеспечивать:

- просмотр подключённых игроков и состояний их заявок;
- назначение персонажей;
- быструю выдачу предметов;
- открытие и скрытие сведений о монстрах, персонажах мира, заданиях и заметках;
- удобную работу во время живой игровой сессии с минимумом действий.

Не добавляй инструменты для карт и наборы сцен на первом этапе, если пользователь явно не изменит приоритеты.

## Текущее состояние

В репозитории есть основа монорепозитория, локальная база SQLite, русскоязычное рабочее место ведущего, создание и переключение кампаний и сессий, подключение игроков по локальной ссылке/QR-коду, обработка заявок, назначение персонажей в рамках сессии, персонажи кампании с постоянным инвентарём, каталог предметов кампании и быстрая выдача из него, автоматическое обновление инвентаря и записи знаний с управляемой видимостью. Миграция `0005` переносит прежние назначения в отдельную таблицу и сохраняет данные персонажей и инвентаря. Есть резервные копии всей SQLite-базы с загрузками и экспорт/импорт кампании с сохранением её сессий, назначений и инвентаря. После импорта сессия с историей игроков считается завершённой; продолжение идёт в новой сессии, чтобы игроки могли подключиться заново без переноса секретов. Рабочее место ведущего разделено на «Подготовку» и режим «За столом»; активная сессия открывается сразу в режиме игры. Интерфейс должен оставаться простым и ориентированным на работу. Визуальное направление — минималистичный детективный нуар; сложный декоративный дизайн пока не нужен.

Любой пользовательский интерфейс должен быть на русском: навигация, подписи, кнопки, проверки ввода, ошибки, доступные названия элементов, уведомления и текст для игроков. Не добавляй английские тексты в интерфейс, если пользователь явно об этом не попросил. Технические имена, идентификаторы, названия API и протокольные значения в коде оставляй без перевода, когда это необходимо для работы.

Не добавляй инфраструктуру без необходимости для текущей задачи. Socket.IO и Zod пока остаются необязательными технологиями и не должны добавляться заранее.

Сервер автоматически применяет подготовленные миграции Drizzle к `data/game.db`. Переменная `PROGDM_DATABASE_FILE` позволяет изменить путь; относительные пути считаются от корня проекта. На чистой базе нет примеров кампаний и сессий. Запрос `/api/session/current` возвращает пустой снимок, если активной сессии нет.

Для чтения и изменения данных ведущего требуется ключ Bearer, который создаётся в `data/dm-key` (рядом с базой, если её путь изменён). Команда `pnpm dm:link` выводит личную ссылку для ведущего; браузер сохраняет ключ локально и удаляет его из фрагмента адреса. Никогда не раскрывай ключ через HTTP-эндпоинт и не считай адрес обратной связи или заголовки прокси подтверждением полномочий: Vite также перенаправляет запросы игроков. Ключ ведущего должен оставаться отдельным от токенов приглашения игроков.

Интерфейс просит подтвердить завершение активной сессии или переключение на другую. Выбранная кампания запоминается. Изменения отключаются, пока запрос выполняется или данные недоступны. Запрос на начало сессии передаёт ожидаемый идентификатор текущей сессии; при несовпадении сервер отвечает HTTP 409. Для проверки интерфейса на временных данных используй изолированный набор `apps/server/test/serve-ui.mjs`, а не рабочую базу.

Изменения схемы базы проводи через `pnpm db:generate` и проверенные миграции, не используя разрушительное обнуление данных. Для ручного применения миграций запусти `pnpm db:migrate`; команда `pnpm test` проверяет сохранение и API на изолированных тестовых базах. Во всех кампаниях может быть только одна активная сессия; при запуске другой предыдущая завершается в транзакции.

## Этапы разработки

1. Готово: локальное сохранение в SQLite и миграции Drizzle.
2. Готово: управление кампаниями и сессиями с защищённым доступом ведущего.
3. Готово: локальные ссылки/QR-коды и заявки на подключение игроков.
4. Готово: принятие заявки ведущим и назначение или создание персонажа.
5. Готово: выдача предметов ведущим персонажу принятого игрока.
6. Готово: сохранение предмета в SQLite и автоматическое обновление инвентаря игрока.
7. Готово: NPC, монстры, заметки и квесты с доступом «скрыто», «одному игроку» или «всей партии».
8. Готово: режимы «Подготовка» и «За столом», справочник предметов кампании для быстрой выдачи, подготовка персонажей и записей знаний до игры.
9. Готово: проверяемые резервные копии базы и загрузок, восстановление со страховочной копией, экспорт и импорт отдельной кампании без переноса секретных токенов.

Следующий этап можно выбрать из более полного профиля персонажа или личных заметок игрока. Сохраняй прежнее ограничение: не добавляй боевые правила и связанные с ними функции.
