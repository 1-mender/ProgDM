# ProgDM

Локальное веб-приложение для ведущего настольных ролевых игр. Ведущий запускает его на ноутбуке, а игроки подключаются со своих телефонов через общую Wi-Fi сеть или точку доступа.

Приложение не требует установки на телефоны, регистрации по почте, интернета, облачного сервера, Docker, PostgreSQL или набора микросервисов.

## Установка и запуск

Установить зависимости:

```bash
pnpm install
```

Запустить сервер и веб-интерфейс:

```bash
pnpm dev
```

Команда `pnpm dev` сначала один раз собирает внутренние пакеты, а затем запускает веб-приложение и сервер. Изменения в `packages/*` автоматически не отслеживаются: после правок там нужно снова выполнить `pnpm build:packages` или перезапустить `pnpm dev`.

Полезные команды:

```bash
pnpm build:packages
pnpm dev:web
pnpm dev:server
pnpm typecheck
pnpm build
pnpm test
```

Адреса по умолчанию:

- Веб-приложение: `http://localhost:5173`
- Проверка состояния сервера: `http://localhost:3333/health`
- Текущая сохранённая сессия: `http://localhost:3333/api/session/current`

## Рабочее место ведущего

Интерфейс ведущего позволяет создавать и выбирать кампании, создавать сессии, начинать и завершать их. При переключении активной сессии и её завершении приложение просит подтверждение. Завершённые сессии остаются в истории, а выбранная кампания запоминается в браузере.

Чтобы получить личную ссылку для входа ведущего, сначала запустите приложение, затем выполните:

```bash
pnpm dm:link
```

Откройте выведенную ссылку на ноутбуке ведущего. Обычно она использует порт `5173`; измените порт в адресе, если Vite запустился на другом. Сервер создаёт случайный ключ в `data/dm-key` (рядом с файлом базы данных, если его путь переопределён). Браузер сохраняет ключ локально и удаляет его из адресной строки. Ключ также можно ввести на экране входа. Кнопка «Выйти» удаляет сохранённый в этом браузере ключ, но не завершает активную игровую сессию.

Не передавайте игрокам ссылку и ключ ведущего. Для игроков приложение показывает отдельные ссылку и QR-код только во время активной сессии. Чтобы подключиться, телефоны должны быть в той же Wi-Fi сети или точке доступа, что и ноутбук. Игрок открывает QR-код или ссылку вида `/join/TOKEN`, вводит имя и ждёт решения ведущего. Ведущий может назначить свободного персонажа или создать нового при принятии заявки; свободных персонажей можно подготовить заранее.

Ссылка работает по обычному HTTP и рассчитана на доверенную локальную сеть. Браузер игрока хранит случайный секрет для этой ссылки, а в SQLite сохраняется только его хеш SHA-256. Игрок может посмотреть только свой статус, назначенного персонажа, его инвентарь и открытые ему знания кампании. Если приложение не обнаружило Wi-Fi адрес ноутбука автоматически, введите его локальный IPv4 адрес в панели ведущего. Переменная `PROGDM_LOCAL_IP` позволяет заранее указать нужный частный IPv4 адрес.

Рабочее место ведущего разделено на режимы «Подготовка» и «За столом». При активной сессии приложение сразу открывает режим игры; переключаться между режимами можно вкладками.

### Перед игрой

1. В режиме «Подготовка» создайте кампанию и запланированную сессию.
2. Заранее добавьте в справочник кампании часто выдаваемые предметы и создайте свободных персонажей. Нажмите имя персонажа, чтобы открыть его профиль: канонические поля и заметки ведущего редактируются здесь же.
3. Подготовьте записи о персонажах мира, монстрах, квестах и фактах. Новые записи всегда скрыты от игроков. Если персонаж больше не участвует в кампании, нажмите кнопку архивации рядом с его именем: его прежние вещи, знания и назначения останутся на месте. Для нового назначения верните его из архива той же кнопкой.
4. В истории сессий нажмите «Начать». Если уже идёт другая сессия, приложение попросит подтвердить переключение.

### Во время игры

1. Откройте QR-код или скопируйте ссылку из блока «Подключение игроков». Телефоны должны быть в той же локальной Wi-Fi сети, что и ноутбук ведущего.
2. Для каждой новой заявки выберите свободного персонажа или создайте персонажа при принятии игрока. Ведущий может отклонить заявку.
3. Чтобы выдать предмет, выберите игрока с назначенным персонажем, предмет из подготовленного справочника и количество, затем нажмите «Выдать». Повторная выдача предмета увеличивает его количество в инвентаре.
4. Чтобы поделиться знанием, выберите аудиторию: конкретного персонажа или всю партию, затем нажмите «Открыть». Кнопка скрывает уже открытую запись. Личное знание останется у персонажа, даже если в следующей сессии его получит другой игрок. Состояние игрока обновляется автоматически, без перезагрузки страницы.

Таким образом, оперативные действия ведущего во время сессии сведены к принятию игрока и назначению персонажа, выдаче предмета, открытию и скрытию подготовленной записи. Создание предметов и знаний, персонажей и сессий находится в режиме «Подготовка». Телефон игрока автоматически обновляет инвентарь и знания примерно раз в три секунды.

### Экран игрока

После принятия заявки игрок видит компактную главную страницу персонажа: имя, текущую сессию, несколько новых событий и последние доступные предметы или знания. Подробности находятся в разделах «Профиль», «Инвентарь», «Знания», «Журнал» и «Заметки». Описание знания открывается нажатием на его название. На вкладке «Профиль» игрок может изменить краткое описание и личную цель персонажа; в «Настройках» — имя своего подключения в текущей сессии. Остальные поля профиля, инвентарь, знания и назначения меняет ведущий.

Личные заметки принадлежат персонажу, сохраняются между сессиями и видны текущему игроку этого персонажа и ведущему. Это догадки и планы игрока, а не подтверждённые факты мира; знаниями партии управляет только ведущий. «Новое» строится по выдачам предметов и открытиям знаний в журнале событий. Кнопка «Просмотрено» убирает пометку новизны, но не удаляет вещи, знания и события. Отметка просмотра хранится у персонажа и переживает смену сессии. Токен завершённой сессии по-прежнему может читать прежний инвентарь и знания, но не получает доступ к новым полям профиля, личным заметкам и отметке просмотра и не может их менять.

### История и проверка данных

В режиме «Подготовка» раздел «История» показывает последние события выбранной кампании: начало и завершение сессий, заявки игроков, назначения, выдачу предметов, изменение видимости знаний, архивирование и восстановление персонажей. Это журнал действий, а не редактор состояния; записи в нём нельзя изменить кнопкой интерфейса. События, произошедшие до появления журнала в миграции `0007`, задним числом не создаются.

Для ручной проверки откройте «Данные и копии» и нажмите «Проверить данные». Если проблем нет, появится сообщение «Проблем не обнаружено». Если проверка найдёт несогласованные записи или недоступный каталог, она покажет причину. Проверка ничего не удаляет и не исправляет: при проблеме сначала создайте резервную копию и разберитесь с причиной, не редактируя рабочую базу наугад. Наличие отдельных файлов загрузок пока нельзя сверить с базой: ссылок на них в таблицах ещё нет.

Все запросы ведущего к API требуют заголовок `Authorization: Bearer <ключ ведущего>`, в том числе запрос `/api/session/current`. Эндпоинт `/health` доступен без ключа. Ответы ведущего не кэшируются. Сервер не считает адрес обратной связи или заголовки прокси подтверждением полномочий ведущего.

| GET | `/api/dm/characters/:id/overview` | Профиль персонажа, текущий игрок, инвентарь, знания, личные заметки и последние события для ведущего |

## Локальная база данных

Для хранения данных используются SQLite, Drizzle ORM и `better-sqlite3`. При запуске сервер создаёт базу `data/game.db` и применяет подготовленные миграции. Путь считается от корня проекта независимо от того, из какой папки запущен сервер. Переменная `PROGDM_DATABASE_FILE` позволяет указать другой путь; относительные пути также отсчитываются от корня проекта.

### Персонажи между сессиями

Персонаж и его инвентарь принадлежат кампании и не привязаны навсегда к записи игрока. Таблица `session_character_assignments` хранит, какой персонаж назначен какому игроку в конкретной сессии. Поэтому старое назначение остаётся в истории завершённой сессии, а в следующей сессии ведущий может назначить тот же персонаж заново. Ограничения базы не позволяют одному игроку получить несколько назначений или назначить одного персонажа двум игрокам в одной сессии.

Персонажа можно архивировать и вернуть в режиме «Подготовка». Архивирование ставит `characters.archived_at`, не удаляя персонажа, инвентарь, знания и назначения из прошлых сессий. Архивного персонажа нельзя назначить в новой сессии; уже назначенного в активной сессии нельзя архивировать. Миграция `0007_typical_miss_america.sql` добавляет этот столбец и таблицу `campaign_activity`. Операции ведущего записывают события в одной транзакции с изменением основных таблиц. История доступна ведущему в компактном разделе «История» и через API; она не заменяет текущее состояние кампании. В событии есть тип, время, ссылки на сущности и краткий текстовый снимок; ключи ведущего, приглашения и хеши токенов игроков туда не записываются. Старые события обычными операциями не редактируются и не удаляются.

Миграция `0008_colorful_franklin_storm.sql` добавляет нейтральные поля профиля, таблицу `character_personal_notes` и отметку просмотра `character_read_state`. Имя, архетип, происхождение, архив и внутренние заметки ведущего меняет только DM. Краткое описание и личную цель могут менять DM и текущий игрок персонажа. Портрет не добавлен: каталоги загрузок есть, но механизма ссылок на файлы и безопасной загрузки пока нет. Существующие персонажи при миграции получают пустые новые поля; старые сведения остаются неизменными.

Миграция `0005_redundant_vin_gonzales.sql` переносит все прежние непустые `characters.player_id` в новую таблицу назначений, используя сессию старой записи игрока, затем убирает старый столбец. Инвентарь по-прежнему ссылается на тот же ID персонажа, поэтому его строки и количество не меняются. Миграция проверяется тестом на базе предыдущей версии с историческим назначением и предметом в инвентаре.

В базе хранятся кампании, сессии, заявки игроков, персонажи, справочник предметов кампании, инвентарь и записи знаний. Справочник принадлежит кампании; выданный предмет связан с персонажем, а одинаковые названия у одного персонажа объединяются в одну запись с общим количеством. Количество должно быть от 1 до 9999. Предметы, уже находившиеся в инвентарях до появления справочника, остаются в базе и продолжают показываться игрокам; новые выдачи выполняются из справочника. Записи знаний относятся к одной из категорий: персонаж мира, монстр, заметка/факт или квест. Их видимость: `hidden` (только ведущий), `party` (вся партия) или `character` (конкретный персонаж кампании). Персональные знания связаны с персонажем, поэтому сохраняются при его повторном назначении в следующих сессиях. Миграция `0006_sudden_the_fury.sql` переносит прежние записи `player` через назначение этого игрока в сессии той же кампании; если назначение нельзя подтвердить, запись остаётся скрытой, а прежний Player и причина фиксируются в `knowledge_migration_issues`. Старые архивы кампаний с персональной видимостью игрока импортируются через историческое назначение; если его нет, знание безопасно остаётся скрытым. Сессия проходит состояния `planned` (запланирована), `active` (активна) и `ended` (завершена). При запуске новой сессии предыдущая завершается в той же транзакции, поэтому активной может быть только одна сессия во всех кампаниях. Завершённые сессии остаются в истории и не могут быть запущены снова.

Название кампании, сессии или персонажа должно содержать от 1 до 120 символов после удаления пробелов по краям. Имя игрока ограничено 60 символами. Заявка привязана к приглашению конкретной сессии и имеет состояние `pending` (ожидает решения), `approved` (принята) или `rejected` (отклонена). Одновременно персонаж может быть назначен не более чем одному игроку.

Пакет базы данных предоставляет `openDatabase()` и операции для кампаний, сессий, заявок игроков, персонажей, справочника предметов, инвентаря и знаний. Миграция `0004_sad_diamondback.sql` добавляет каталог предметов кампании и необязательную ссылку на него у записи инвентаря, не удаляя прежние предметы. Идентификаторы, временные отметки и случайные токены приглашений генерируются автоматически. Страница игрока обновляет статус, инвентарь и знания опросом примерно раз в три секунды; Socket.IO для текущего обмена не используется.

Запрос `GET /api/session/current` возвращает `{ "snapshot": null }`, если база пуста или активной сессии нет. В противном случае `snapshot` содержит сохранённые `campaign` и `session`. Примеры данных автоматически не добавляются.

### Миграции и обслуживание

```bash
pnpm db:generate
pnpm db:migrate
pnpm test
```

При изменении схемы отредактируйте `packages/database/src/schema.ts`, создайте миграцию и проверьте SQL и метаданные в `packages/database/migrations` перед применением. Команда `pnpm db:migrate` собирает внутренние пакеты и применяет ожидающие миграции, не запуская сервер. Повторный запуск не удаляет и не перезаписывает существующие записи. Описание процесса находится в [документации Drizzle](https://orm.drizzle.team/docs/drizzle-kit-generate).

### Резервные копии и перенос кампании

В режиме «Подготовка» откройте раздел «Данные и копии». Создание копии использует согласованный снимок SQLite, поэтому сервер можно не останавливать. Копия базы и соответствующая папка `progdm-backup-…-uploads` сохраняются в `data/backups`; из интерфейса скачивается файл базы. Для переноса копии на другой компьютер сохраните оба элемента с одинаковым идентификатором. Восстановление заменяет текущую базу и файлы загрузок, предварительно создавая страховочную копию. Приложение проверяет целостность базы и ссылок перед восстановлением.

Кнопка «Проверить данные» запускает `integrity_check`, `foreign_key_check`, сверку применённых миграций с текущим журналом, проверку доступности каталогов базы/копий/загрузок и проверку связей между кампаниями у назначений, знаний, инвентаря и событий. Ничего автоматически не исправляется. В БД пока нет ссылок на отдельные upload-файлы, поэтому проверить отсутствие конкретных файлов невозможно; эта часть явно отмечена в результате. Восстановление копии сохраняет журнал и архивное состояние и добавляет событие `backup_restored` для каждой восстановленной кампании. Старый совместимый backup сначала мигрируется во временной копии; исходный файл не изменяется.

Экспорт кампании создаёт файл JSON со всеми её сессиями, игроками, историей назначений, персонажами, инвентарём, справочником предметов и знаниями. Ключи приглашений и секреты игроков в файл не попадают. Импорт добавляет отдельную кампанию и создаёт новые идентификаторы и секреты. Активная сессия и любая сессия с записями игроков импортируются завершёнными: их история и назначения сохраняются, но запускать их повторно нельзя. Чтобы продолжить игру, ведущий создаёт новую сессию; игроки подключаются к ней заново и могут использовать прежние имена и персонажей. Запланированная сессия без игроков сохраняет статус. Существующие кампании не перезаписываются.

JSON-экспорт версии 3 включает `archivedAt`, поля профиля, личные заметки персонажей и историю событий. Ссылки событий на сессии, игроков, персонажей, предметы и знания хранятся типизированными полями и при импорте переназначаются на новые ID; текстовый payload допускает только безопасные краткие поля без секретов и ID. Файлы версий 1 и 2 по-прежнему импортируются; отсутствующие в них поля профиля и заметки остаются пустыми. Отметка «просмотрено» хранится в локальной базе для персонажа, но не входит в переносимый экспорт кампании; после импорта старые релевантные события могут снова выглядеть новыми, пока игрок их не отметит. Backup/restore, напротив, сохраняет отметки вместе со всей базой. Импорт фиксируется отдельным событием `campaign_imported`; сессии, которые при импорте становятся завершёнными, получают событие `session_ended`.

Внешние ключи, проверки допустимых состояний, уникальные токены приглашений и частичный уникальный индекс защищают целостность данных. SQLite работает в режиме WAL. Файлы с данными исключены из Git, а схема и миграции хранятся в репозитории.

Тесты используют отдельные временные базы данных. Они проверяют сохранение данных между процессами, повторное применение миграций, ограничения, переходы состояний сессий, откат транзакций и API сервера. Тесты не заполняют рабочую базу.

Для ручной проверки интерфейса на временных данных сначала соберите проект, затем выполните `node apps/server/test/serve-ui.mjs`. Команда запускает доступный только на этом компьютере API на порту `3334` с базой в памяти и фиксированным тестовым ключом `progdm-ui-test`. Запустите отдельный экземпляр Vite на порту `5174`, указав `PROGDM_API_TARGET=http://127.0.0.1:3334`, и откройте `http://localhost:5174/#dm=progdm-ui-test`. Не используйте этот тестовый сервер как обычное рабочее приложение.

## Автоматические проверки GitHub

Workflow `.github/workflows/ci.yml` запускается после push в `main` и для Pull Request в `main`. Он работает на Ubuntu с Node.js 24 LTS; `pnpm/action-setup` читает закреплённую версию pnpm из `packageManager` в корневом `package.json`. Corepack отдельно не нужен.

Зависимости устанавливаются командой `pnpm install --frozen-lockfile`. Кешируется только хранилище pnpm по `pnpm-lock.yaml`, а не `node_modules` или результаты тестов. Затем выполняются `pnpm test` (включая `pnpm typecheck`, database/server/web tests) и `pnpm build`. Локальные scripts не изменены: отдельный повторный typecheck в CI не нужен.

Whitespace проверяется по diff между предыдущим и новым SHA push либо по diff PR от merge-base. Если предыдущий SHA отсутствует (например, первый push новой ветки), проверяется последний коммит через `git show --check`. Обычный `git diff --check` остаётся локальной проверкой незакоммиченных изменений.

CI не запускает рабочий сервер и не требует ключа ведущего, пользовательской базы, настоящих токенов или секретов GitHub. Тесты используют тестовые данные; рабочая папка `data` не публикуется. Деплой и релизы не выполняются. Результат проверки доступен во вкладке Actions репозитория и в status checks коммита/PR.

## Границы проекта

ProgDM — общая память партии и пульт ведущего для управления тем, что известно игрокам. В продукт входят профили игроков, персонажи, инвентарь, задания и сведения о персонажах мира и монстрах, которые ведущий открыл игрокам.

Боёвка, встречи с противниками как игровая механика, инициатива, очки здоровья, урон и лечение исключены из проекта. Монстры хранятся как записи знаний, а не как боевые единицы.

Сейчас в проекте работают экран кампаний и сессий ведущего, локальное подключение игроков по QR-коду, принятие заявок и назначение персонажей, выдача предметов из подготовленного справочника с автоматическим обновлением инвентаря, знания кампании с управляемой видимостью и автоматическим обновлением на телефоне, режимы ведущего «Подготовка» и «За столом», нейтральный профиль персонажа, личные заметки, компактный экран игрока, журнал событий, архивирование персонажей, ручная проверка данных, резервные копии, перенос кампаний и локальное сохранение. Финальный визуальный стиль пока не разработан.
